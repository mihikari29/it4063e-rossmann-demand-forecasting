## Monitoring design and trade-offs

This is a separate retrospective-development / synthetic adapter, not Phase 13 M5 or a production
ingestion service. It accepts already-authorized in-memory forecast and label records only; no
source discovery/reader, target generation, fitting, retraining or protected-period dates.
Forecast keys include Store, origin, target, horizon and model identity. Each row retains issuance
identity/hash and evidence kind. Labels have Store/target/availability dates and source Open.
Validate uniqueness, H1..14 date arithmetic, issue-before-target, label-after-target and as-of
availability; reject ambiguous joins and unexpected labels. Missing labels/predictions remain null.
Preserve observed closures/zero Sales and report them separately. Compare one model/evidence kind
at a time. Metrics reuse the accepted Open=1 implementation and explicit MAPE/WAPE denominators.
Daily/trailing 7/14-calendar-day summaries retain origin, Store/horizon strata and partial flags.
Reference windows precede current windows and cannot overlap. Feature comparisons accept only
issuance-time, origin-known features with an availability declaration; no target/Customers fields.
Use missingness, frequencies and numeric quartiles/median difference, without KS/p-values or
numeric drift/performance alarms. Constant/small populations are explicit. Human review can inspect
differences; broader numeric thresholds and persistence remain proposed and unactivated.

This deliberately chooses the already accepted descriptive approach over adding Evidently and
an unvalidated trigger policy. The old three-day rule is removed, not claimed as implemented.
Synthetic report status describes evidence availability, never system health. All generated views
share one summary/status/time/window payload; no separate fixed dashboard status.
